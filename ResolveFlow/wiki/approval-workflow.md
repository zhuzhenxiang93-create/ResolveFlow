# 本地独立审核入口

## 简洁输出与恢复诊断

用户与审核CLI默认显示答案、进度、当前审批及下一步；完整JSON通过 `/debug` 按需获取。
审核员 `/show` 无参数时刷新当前选中任务；从未选中则提示提供任务ID。
恢复后从新的工具会话边界执行，原始工具历史仍持久化但不再原样发给模型。
每轮最后附服务器当前计划、已核验目标、已完成动作、有效证据、待重查工具和确认审批状态。
无工具调用最多获得一次纠正机会（整个任务累计，重启或人工恢复不重置），并消耗正常步骤/模型预算。
纠正失败或异常不能切换为规则降级。记录停止原因、允许工具、文本是否存在及长度，不记录原始模型正文或隐式思维链。
本次改造以离线回归验证；不代表用户原任务已恢复成功，未自动操作该任务或进行付费复验。

本地模拟角色分离，不是生产 IAM：同一系统用户拥有 SQLite 和凭据文件，可绕过本地角色。
生产需要独立账号、租户权限、审计持久化与受控业务服务。本入口只监听 127.0.0.1。

## 启动

仓库根目录或后端目录均可执行：

1. `make approval-init`：首次创建 .env.approval.local，权限0600，生成 JWT 签名密钥 `AGENT_JWT_SECRET`
   和令牌签发引导密钥 `AGENT_ADMIN_SECRET`（两者用途不同：前者签发/校验所有角色的 JWT，后者只用于
   `/agent/auth/token` 这个非 JWT 的根信任点）；不打印密钥，不覆盖已有文件。
2. 终端A：`make approval-server`，默认端口8766，不影响8000上的旧服务。读 .env.agent.local 模型配置，使用与用户CLI相同的 AGENT_STATE_PATH（默认 data/agent/state.sqlite3）。
3. 终端B：`make agent-review`。此客户端只通过HTTP操作，不直接修改数据库；启动时用本地读到的
   `AGENT_JWT_SECRET` 就地签发一个 `role=reviewer`、`subject=local-reviewer` 的短期 JWT，不再是比较
   一个固定共享密钥字符串——同机文件访问仍是既有信任边界，没有变成远程身份系统。
4. 终端C：`make agent-chat`，用户继续自己的确认流程。

端口被占用时，从根目录运行 `PYTHONPATH=ResolveFlow .venv/bin/python ResolveFlow/scripts/approval_service.py --port 8767`，客户端使用 `PYTHONPATH=ResolveFlow .venv/bin/python ResolveFlow/scripts/approval_cli.py --url http://127.0.0.1:8767`。

## 审核流程

`/list` 显示最近100个待审批或需要人工处理的任务。
`/show 任务ID` 显示当前订单、历史工具证据、用户确认、待批参数、版本及过期状态。历史证据不等于当前事实。
`/approve 审批ID` 或 `/reject 审批ID` 必须对应刚查看的任务；输入 YES 后才提交。
服务器再次校验用户确认、审批对象、参数、版本、有效期和业务条件，客户端显示不能代替这些检查。
批准后原编排服务继续任务，拒绝则停止退款，保留已经完成的其他动作。
HTTP响应超时不会自动重试写操作，须先 /show 查询最终状态。

## 失效审批恢复

先 `/show 任务ID` 审核原目标及已完成动作。只有目标仍适用，才 `/release 任务ID` 并输入 YES。
release 不是批准：旧确认失效，旧审批归档，原任务重新检查业务状态并要求新的用户确认。
若目标已改变，应由用户 revise，而非审核员盲目恢复原目标。
用户端 `/resume 任务ID` 查看新的确认，确认后生成全新审批。审核员重新 /show，再决定批准或拒绝新审批。
已失效审批不能复活。预算耗尽的任务不能靠 release 重置预算。

启动服务和查看队列不调用模型；恢复或批准后若仍需执行工具，可能调用真实模型并计费。
本次自动验证仅用临时库和离线模式，未对用户当前订单进行任何恢复、确认或审批。
