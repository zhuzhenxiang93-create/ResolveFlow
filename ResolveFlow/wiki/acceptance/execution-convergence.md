# 业务执行收敛与模糊退款处理

本次改动基于现有 Commerce 增量收敛，替代应用入口按资料是否存在回退旧 ActionRuntime 的行为。

## 统一链路

认证身份 → 统一对话 → 区分咨询与办理 → 必要澄清 → 查询本人业务记录 → 绑定业务对象和操作 → 确定性资格与金额计算 → 用户确认 → 必要的独立审批 → 模拟执行 → 状态核验。

业务域可以暂时未知。统一执行不要求在第一句话确定商品或订阅，也不意味着两种业务使用相同资格政策。

| 用户表达 | 行为 | 不允许的副作用 |
| --- | --- | --- |
| 退款有什么条件？ | 询问商品或订阅；回答“订阅”后查询对应政策 | 不创建申请 |
| 我要退款 | 查询本人记录，展示商品及订阅候选 | 模型不得自行挑选对象，只有一条记录也不能默认提交 |
| 退掉这笔商品，会员别续了 | 分别绑定对象和操作 | 退款不能隐式取消另一项权益 |
| 取消订阅、退订 | 关闭未来续费，保留已付费周期权益 | 不自动退款或立即撤销权益 |

## 架构选择及兼容性

- `/chat`、`/agent/conversation` 和 `/agent/tasks` 的开始请求进入同一 ConversationService / Commerce 链路；最后一个接口现在返回对话信封，旧客户端需更新。
- 应用工厂使用 ExecutionContext。旧任务可按身份只读查询；旧确认、执行、修改和审批接口返回 410，不将旧确认转换成新授权。
- ActionRuntime 源码保留供历史单元测试和离线脚本使用。没有宣称整个仓库已经删除旧实现。
- 旧计数式订阅数据只迁移为证据不完整的快照，不编造金额、账单或周期；需要补充真实业务证据后才能办理。
- 演示政策更新为 demo-commerce-v2。旧政策报价不能直接沿用原确认。
- 前端移除旧任务操作面板，Commerce 面板承载当前业务。
- 新增退款咨询上下文按用户和会话隔离；删除记忆也清除该上下文。

## 本次验证

执行命令：后端 `make test`；前端 `npm run build`。

本次完整运行发现 305 项测试，296 项通过，9 项跳过；前端生产构建通过。测试覆盖入口政策一致、旧授权失效、身份隔离、确认/审批、历史任务只读、模糊咨询多轮澄清及阻止模型擅自选对象。旧运行时的底层安全回归仍保留；原应用入口测试改为验证新公共契约。

这些结果是本次自动化测试及构建证据，不代表本次真实模型、真实 Redis/Chroma 或浏览器重新验收完成。之前 acceptance 报告中的端到端结果属于之前版本，不自动适用于本次修改。外部支付仍为模拟，不能声称真实到账。

## 局限及后续验证

模糊表达仍依赖模型提取和服务端约束共同处理；不能凭有限测试宣称覆盖所有自然语言。裸退款表达有确定性保护，其他复杂表述需要持续加入对抗及多轮样例。旧离线执行脚本后续可归档或移除；应用入口已不再回退旧执行器。发布前应补跑真实模型与浏览器关键流程。
