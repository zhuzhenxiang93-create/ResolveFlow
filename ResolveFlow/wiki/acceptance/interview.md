# ResolveFlow 面试材料（按实证表述）

## 项目介绍

ResolveFlow 是统一对话入口的售后助手，基于 FastAPI、Vue、SQLite、Redis、Chroma。模型将自然语言转换为业务意图，服务端再用认证身份查询实际购买记录，处理消歧并计算确定的资格和金额。商品退款和订阅退款通过对象绑定的确认、独立审核、状态核验进入模拟执行。知识库回答一般政策，记忆减少重复表达，但两者都不能授予资金操作权限。

本次是现有项目增量完善，复用了原有 JWT、审核边界、工具与混合检索。没有重建一套 Java 服务，也没有为展示技术栈而迁移 PostgreSQL。所有资金结果都是测试环境模拟，不能说成真实商家接入或生产收益。

## 典型故障叙述

1. 首次浏览器商品退款没有完成，排查发现真实模型返回的item_id实际是订单ID。服务端拒绝了错误归属，没有产生退款。修复工具参数枚举和语义绑定后，再次从聊天、确认到独立审核及模拟回执完整验证。
2. 页面显示画像把“退商品、停续费”当作偏好。将提取输入收窄到用户显式长期偏好，排除临时要求和助手文本；提供查看、纠正、删除入口。验证删除后摘要和画像不会立即还原。
3. 增加文档同版本冲突检查后，旧的未版本化文档更新测试失败。保留旧内部调用兼容，显式版本文档要求升级版本；没有删除原检索同步断言。
4. 业务决定已提交后记忆写入异常可能返回500，让用户误以为业务失败。将记忆写入与已提交结果分开，保留业务结果并报告降级；新增故障注入测试。

## 常见追问

- **为什么不是全交给模型？** 模型处理语义，不负责真实身份、可退款额和权限。提示词不足以保障幂等或防止越权。
- **记忆有什么可量化作用？** 本次受控样例中开启记忆从一次澄清降到零次，简洁偏好从122字符降为53字符，金额一致。这是小样本机制验证，不是线上平均收益；耗时按原始结果报告。
- **如何证明用到了真实模型？** 单独保存真实调用账本和HTTP响应；mock仅用于确定性故障与权限测试。真实模型预算最多60次，不能把所有295项单测说成真实模型通过。
- **为什么SQLite？** 当前单机演示足够，并能快速复现事务和迁移。生产并发、跨服务账务要评估PostgreSQL、Outbox、渠道对账，已有PG POC未被包装成生产能力。
- **记忆是否影响资格？** 不影响。偏好改变表达，历史提供指代候选，业务事实始终重新读取数据库。
- **可执行政策与知识冲突怎么办？** 退款必须由确定性规则授权；普通知识上传不改变金额和权限。生产需政策发布审核、版本绑定与冲突检测。

已验证：report.md列出的本次单测、真实依赖、真实模型及浏览器证据。
未来规划：生产渠道、多worker记忆、全历史计费周期、跨ID政策治理、持续负载评估。没有编造生产准确率、召回率、节省人力或业务增长。
